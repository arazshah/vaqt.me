تصمیم‌های فرآیندی ثبت‌شده در همین بازبینی (بند ۳ و ۷ اسپک فاز ۴):

- از این پس تگ‌های فاز همیشه annotated ساخته می‌شوند (`git tag -a`)، نه lightweight.
- برنچ پیش‌فرض مخزن از این پس `main` است (نه `master`)؛ CI و branch protection فقط

- از فاز ۴ به بعد، انتهای هر گزارش فاز باید یک جدول self-audit داشته باشد: هر بند

  می‌خورند (نمونه در انتهای یادداشت‌های فاز ۴ پایین).
- **جریان کاری git از این پس PR-محور است، نه push مستقیم به `main`.** با فعال شدن
  کامل `branch protection` (بند بالا: `required_status_checks: ["ci"]` +
  `enforce_admins: true`)، push مستقیم به `main` عملاً رد می‌شود (تأیید زنده،
  ۲۰۲۶-۰۸-۲۱: `git push origin main` با خطای `GH006: Protected branch update failed`
  رد شد چون هیچ ران CI‌ای هنوز برای آن SHA وجود نداشت). از این پس: هر تغییر روی یک
  برنچ جدا، `gh pr create`، صبر برای سبز شدن `ci`، سپس `gh pr merge --rebase` (نه
  squash، تا کامیت‌های جداگانه روی `main` حفظ شوند). **بدون bypass** — `enforce_admins`
  یعنی حتی مالک مخزن هم از این قاعده مستثنا نیست؛ گزینه‌ی `--admin` در `gh pr merge`
  عمداً هرگز استفاده نشد (حتی برای اثبات مسدودشدن یک PR با تست شکسته — به پایین
  مراجعه شود)، چون ریسک واقعی merge شدن کد شکسته را داشت.
  - **اثبات منفی (۲۰۲۶-۰۸-۲۱):** یک PR با یک assertion عمداً غلط در
    `packages/shared/src/schemas/money.test.ts` باز شد (`#2`)؛ CI واقعاً fail کرد،
    `gh pr view --json mergeStateStatus` مقدار `BLOCKED` برگرداند، و
    `gh pr merge --rebase` با پیام «the base branch policy prohibits the merge» رد
    شد. PR بدون merge بسته و برنچ حذف شد.

## قانون Merge — جدا از سبز شدن CI

> **این بخش عمداً جدا و با تیتر روشن نوشته شده تا دیگر «رویه‌ی PR-محور» بالا به معنای
> مجوز دائمی merge خوانده نشود.** بازبینی ۲۰۲۶-۰۸-۲۱: PRهای #۱۰، #۱۱، #۱۲ بدون
> دستور جداگانه‌ی کاربر merge شدند — نه به این دلیل که واقعاً مجاز بود، بلکه چون
> توضیح رویه‌ی بالا (خط ۵۲ تا ۶۶) به‌اشتباه به‌عنوان «همیشه همین‌طور ادامه بده»
> تفسیر شد. این سه قاعده آن ابهام را می‌بندد:

1. **سبز شدن CI شرط لازم برای merge است، نه مجوز merge.** یک PR با CI سبز هنوز
   نباید merge شود تا کاربر صریحاً همان PR را نام ببرد.
2. **هر merge نیازمند دستور جداگانه برای همان شماره‌ی PR است.** «ادامه بده» یا
   «این کارها را بکن» در یک پیام، مجوز merge برای PRهای بعدی که از دل همان کار
   بیرون می‌آیند نیست — حتی اگر کاربر قبلاً یک PR مشابه را merge کرده باشد.
3. **ساخت PR (`gh pr create`) آزاد و بدون نیاز به تأیید جداگانه است** — چون
   PR باز صرفاً یک پیشنهاد قابل‌بازبینی است، ریسکی ندارد. فقط `gh pr merge` نیاز
   به دستور صریح دارد.

### به‌روزرسانی مجوز — کار خودمختار از ۲۰۲۶-۰۸-۲۳

از تاریخ ۲۰۲۶-۰۸-۲۳، کاربر صریحاً قاعده‌ی ۲ بالا را برای ادامه‌ی کار روی فاز ۶ (و
هر فاز بعدی، تا اطلاع ثانوی) کنار گذاشت: دیگر نیازی به دستور جداگانه به‌ازای هر
شماره‌ی PR نیست. قاعده‌ی جدید:

- **merge خودکار مجاز است فقط وقتی CI واقعاً سبز است** — قاعده‌ی ۱ («سبز شدن CI
  شرط لازم است») همچنان کاملاً پابرجاست، فقط دیگر شرط کافی هم هست.
- بعد از هر merge، ادامه‌ی مستقیم به سراغ کار بعدی بدون توقف برای «ادامه بدهم؟»
  — طبق دستور صریح کاربر: «After each PR merges, immediately pick the next task
  yourself and keep going».
- تصمیم‌های پیاده‌سازی کوچک (چیدمان UI، متن پیام خطا، ساختار فایل، تقسیم PR) بدون
  توقف برای تأیید گرفته می‌شوند؛ تصمیم باید همین‌جا یا در توضیح PR مستند شود، نه
  فقط در پاسخ چت.
- توقف و پرسش از کاربر فقط برای سه مورد: (۱) تصمیم‌های محصولی که رفتار قابل‌مشاهده
  برای کاربر نهایی را به‌شکل غیربدیهی تغییر می‌دهند، (۲) اقدام‌های غیرقابل‌برگشت
  (force-push، merge بدون CI سبز، حذف داده)، (۳) گیر کردن واقعی (مثل مشکل فضای
  دیسک `/tmp` در بازبینی قبلی).
- **الزام سخت‌گیرتر جایگزین**: هر PR باید تست واقعی روی Postgres/Redis واقعی
  داشته باشد (نه mock)، و خروجی واقعی دستور اثبات آن (نه فقط خلاصه) نشان داده شود.

این مجوز محدود به merge است — قاعده‌ی ۱ و ۳ بالا و کل بخش «PRهای پیش از
خلاصه‌سازی context» (که دقیقاً همین ریسک را نشان می‌دهد: تفسیر گسترده‌تر از یک
مجوز محدود) بدون تغییر باقی می‌مانند برای هر کاری که این مجوز صریح را نداشته باشد.

## PRهای پیش از خلاصه‌سازی context — وضعیت تأیید نامعلوم

بازبینی ۲۰۲۶-۰۸-۲۱: حافظه‌ی این دستیار از بخشی از همین نشست (پیش از یک

### ۱۱. Idempotency کالبک زرین‌پال

بله، کاملاً idempotent:

- قید unique روی `Order.authority`
- کالبک داخل یک تراکنش با `SELECT ... FOR UPDATE` روی سفارش اجرا می‌شود
- اگر وضعیت از قبل `PAID` بود:
  - verify دوباره صدا زده نمی‌شود
  - همان `refId` برگردانده می‌شود
  - Entitlement جدید ساخته نمی‌شود
- کالبک هرگز مستقیم به کاربر HTML نشان نمی‌دهد؛ فقط `302` به `/payment/result?order=...`
- مقایسه‌ی مبلغ برگشتی با مبلغ سفارش الزامی
- در صورت عدم تطابق → `FAILED` + `AuditLog`
- سفارش‌های `PENDING` قدیمی‌تر از ۳۰ دقیقه با job آشتی‌سازی بررسی و بسته می‌شوند

### ۱۲. منبع حقیقت enum‌ها (فاز ۱)

- تمام enum‌های سیستم در `packages/shared/src/constants/enums.ts` به‌صورت `as const` + `z.enum` تعریف می‌شوند؛ `prisma/schema.prisma` آینه‌ی همین مقادیر است

- تست واحد `packages/db/src/__tests__/enums.test.ts` برابری مقادیر هر enum بین دو طرف را assert می‌کند؛ در صورت drift، تست fail می‌شود (تأیید شد با یک drift موقت عمدی)

### ۱۳. هش OTP (فاز ۱ — جایگزین بند ۷۱ PROJECT_SPEC)

- به‌جای bcrypt، از **HMAC-SHA256 با pepper سمت سرور** استفاده می‌شود
- pepper در env متغیر `OTP_PEPPER` (اضافه‌شده به `apps/api/.env.example`)
- مقایسه‌ی کد وارد‌شده با هش ذخیره‌شده حتماً با `crypto.timingSafeEqual` انجام شود (نه `===`)
- پیاده‌سازی واقعی هش/مقایسه در فاز ۲ (احراز هویت) انجام می‌شود؛ در فاز ۱ فقط فیلد `VerificationCode.codeHash` (String) و env var آماده شدند

### ۱۴. Offer — یکتایی سخت + رفتار re-submit

- قید `@@unique([requestId, providerId])` سخت باقی می‌ماند (هر ارائه‌دهنده فقط یک رکورد Offer به‌ازای هر درخواست)
- ارسال مجدد پیشنهاد پس از `WITHDRAWN`، رکورد یکسان را به‌جای رکورد جدید به `PENDING` برمی‌گرداند و `revisionCount` را یک واحد افزایش می‌دهد (پیاده‌سازی منطق در سرویس فاز ۶؛ فیلد `revisionCount` در فاز ۱ به مدل اضافه شد)

### ۱۵. مهارت‌های درخواست — جدول واسط

- ارتباط Request↔Skill به‌جای `String[]` با جدول واسط `RequestSkill` (کلید ترکیبی `requestId`+`skillId`) پیاده شده تا یکپارچگی ارجاعی و امکان کوئری معکوس (کدام درخواست‌ها فلان مهارت را دارند) حفظ شود

### ۱۶. جست‌وجوی فارسی

- افزونه `pg_trgm` در migration اول فعال شده (`CREATE EXTENSION IF NOT EXISTS pg_trgm;`)
- ستون `Request.searchText` در زمان نوشتن (create/update سرویس) با `normalizeFa(title + ' ' + description)` پر می‌شود — نه به‌صورت generated column در دیتابیس
- ایندکس `GIN` با `gin_trgm_ops` روی `searchText` (اضافه‌شده با SQL خام به migration، نه از طریق attribute بومی Prisma، چون خروجی مستقیم و قابل‌پیش‌بینی‌تر است)
- تابع `normalizeFa()` در `packages/shared/src/utils/normalize-fa.ts`: تبدیل ي/ك عربی به ی/ک، حذف اعراب و تطویل (tatweel)، تبدیل ارقام فارسی/عربی به لاتین، یکسان‌سازی نیم‌فاصله (ZWNJ) به فاصله‌ی معمولی، یکسان‌سازی فاصله‌ها — با ۱۰ تست واحد
- تأیید شد: seed شامل یک درخواست (`req-thesis-literature`) با ي عربی در توضیحات است؛ کوئری trigram با نسخه‌ی نرمال‌شده‌ی همان عبارت با موفقیت آن را پیدا می‌کند

### ۱۷. نرمال‌سازی شماره موبایل (فاز ۲)

- تابع `normalizePhone()` در `packages/shared/src/utils/normalize-phone.ts`، دقیقاً به سبک `normalizeFa()` (همان انضباط: هر کاراکتر غیر-ASCII فقط با escape صریح `\uXXXX`، نه glyph کپی‌شده)
- ورودی‌های مجاز: `09xxxxxxxxx`، `9xxxxxxxxx`، `+989xxxxxxxxx`، `00989xxxxxxxxx` — با ارقام فارسی/عربی، فاصله یا خط تیره؛ همه به شکل canonical `+989xxxxxxxxx`
- هر چیز دیگری `null` برمی‌گرداند؛ در DB (`User.phone`) فقط شکل canonical ذخیره و `@unique` می‌شود
- ۱۸ تست واحد (تمام شکل‌های معتبر + رد موارد نامعتبر)

### ۱۸. ذخیره‌سازی و تأیید OTP

- کد در `VerificationCode.codeHash` با HMAC-SHA256 + `OTP_PEPPER` ذخیره می‌شود؛ Postgres هرگز کد خام را نمی‌بیند
- مقایسه با `crypto.timingSafeEqual`؛ وقتی کد فعالی برای شماره وجود ندارد هم یک HMAC روی مقدار dummy محاسبه و مقایسه می‌شود تا زمان پاسخ بین «کد وجود ندارد» و «کد اشتباه است» یکسان بماند (کد OTP هرگز شماره را لو نمی‌دهد)
- Redis فقط برای شمارنده‌های rate limit و یک کش کوتاه‌مدت «کد در انتظار» (`OtpPendingCodeStore`) استفاده می‌شود — نه برای اعتبارسنجی؛ منبع حقیقت تأیید همیشه Postgres + HMAC است
- ارسال مجدد: تا انقضای کد فعلی، همان کد دوباره صف می‌شود و `expiresAt` تمدید نمی‌شود؛ حداکثر ۳ ارسال برای هر کد (`sendCount`، فیلد جدید روی `VerificationCode`). اگر کش Redis کد در انتظار را از دست بدهد (مثلاً ری‌استارت)، یک کد تازه برای همان ردیف صادر می‌شود بدون تمدید `expiresAt`

### ۱۹. Rate limiting چندلایه (Redis sorted-set sliding window)

پنج لایه، همه با آستانه‌ی قابل‌تنظیم از env (پیش‌فرض‌ها در `apps/api/.env.example`):

1. ارسال مجدد OTP برای هر شماره: حداکثر ۱ در ۶۰ ثانیه
2. هر شماره: ۵ در ساعت، ۱۰ در شبانه‌روز
3. هر IP: ۱۵ در ساعت، ۴۰ در شبانه‌روز
4. تأیید: حداکثر ۵ تلاش برای هر کد (سپس کد باطل می‌شود)
5. پس از ۳ کد باطل‌شده‌ی متوالی برای یک شماره: بلاک ۳۰ دقیقه‌ای (کلید جدا در Redis، مستقل از شمارنده‌های بالا)

پیاده‌سازی sliding window با Redis sorted set (`ZADD`/`ZREMRANGEBYSCORE`/`ZCARD`) — هر تلاش (حتی رد‌شده) یک slot اشغال می‌کند تا کوبیدن endpoint نتواند پنجره را دور بزند.

### ۲۰. JWT و مدیریت نشست (Session)

- access token ۱۵ دقیقه، refresh token ۳۰ روز؛ هر دو httpOnly + `SameSite=Lax` + `Secure` فقط در production. مسیر کوکی refresh محدود به `/api/v1/auth`
- payload توکن حداقلی: فقط `sub` (userId) و `sid` (sessionId) — نقش و وضعیت تأیید در توکن نیستند، همیشه از DB خوانده می‌شوند
- مدل `Session` (migration جداگانه در فاز ۲، چون در فاز ۱ ساخته نشده بود): `refreshTokenHash` (SHA-256، `@unique`)، `familyId`، `userAgent`، `ip`، `expiresAt`، `revokedAt`، `replacedById`
- چرخش refresh token: هر `refresh` یک ردیف `Session` جدید می‌سازد و قبلی را `revokedAt` می‌کند (اتمیک، در یک تراکنش). اگر توکنی که از قبل `revokedAt` دارد دوباره ارسال شود → **کل family** (`revokeFamily`) باطل می‌شود و یک `AuditLog` با `severity: high` ثبت می‌شود، حتی برای نشست‌های دیگرِ همان family که خودشان هرگز replay نشده بودند
- تأیید زنده روی سرور واقعی: replay یک refresh token منقضی‌شده، هر دو نشست خانواده (نشست اصلی + نشست جایگزین قانونی) را در Postgres واقعی `revokedAt` کرد؛ درخواست refresh بعدی با همان کوکی «قانونی» هم رد شد

### ۲۱. گاردها

- `JwtAuthGuard`: سراسری (`APP_GUARD`) و fail-closed؛ فقط signature/expiry توکن را چک می‌کند (بدون hit به DB)، باز کردن روت فقط با `@Public()`. توکن از کوکی `access_token` یا هدر `Authorization: Bearer` خوانده می‌شود (کوکی اولویت دارد)
- `RequireVerifiedPhoneGuard`: `phoneVerifiedAt` و `status` را از DB می‌خواند (نه JWT)، با کش ۳۰ ثانیه‌ای در Redis؛ لغو تأیید در DB حداکثر پس از انقضای کش (نه انقضای access token ۱۵ دقیقه‌ای) اعمال می‌شود — تأیید شد با تست مستقیم گارد (کش دستی flush شد، بدون صبر واقعی)
- `RequireOwnershipGuard` + دکوریتور `@RequireOwnership(resolver)`: عمومی و آماده برای فازهای بعد؛ resolver مالک منبع را برمی‌گرداند، `null` → 404، مالک نامطابق → 403 (برای جلوگیری از leak وجود منبع)

### ۲۲. آداپتر پیامک و صف

- اینترفیس `SmsPort` با `sendOtp` / `sendNotification`؛ `MockSmsAdapter` (کد را فقط خارج از production لاگ می‌کند) و `SmsIrAdapter` (API الگو/verify واقعی sms.ir)
- `DEV_FIXED_OTP` برای تست‌های e2e (فقط خارج از production)
- assertion سخت در bootstrap: `SMS_PROVIDER=mock` با `NODE_ENV=production` باعث throw در ساخت provider می‌شود و برنامه بالا نمی‌آید (تأیید شد با اجرای واقعی)
- ارسال از صف BullMQ با نام `sms` عبور می‌کند (۳ retry، backoff نمایی)؛ خطای صف (مثلاً Redis موقتاً در دسترس نیست) لاگ می‌شود ولی هرگز پاسخ HTTP را بلاک نمی‌کند
- **اتصال Redis مشترک BullMQ در `BullRedisModule` (`BullModule.forRootAsync`) در سطح `AppModule` تنظیم شده** — طبق تصمیم فاز ۰ («یک اتصال Redis مشترک»)؛ این یک باگ واقعی بود که موقع اجرای زنده کشف شد (بدون آن BullMQ با خطای «Worker requires a connection» بالا نمی‌آمد چون `BullModule.registerQueue()` به‌تنهایی connection نمی‌سازد)

### ۲۳. لاگ، Audit و خطاها

- شماره‌ها همه‌جا (لاگ‌ها، `AuditLog.meta`) با `maskPhone()` ماسک می‌شوند: `+98912***4567`
- `AuditLog` برای: ورود موفق، شکست تأیید (با/بدون رسیدن به سقف تلاش)، بلاک شدن شماره، تشخیص reuse (severity: high)، logout، logout-all
- کدهای خطای ماشین‌خوان در `apps/api/src/common/errors/error-codes.ts`، پیام فارسی متناظر در `apps/api/src/common/messages/fa.ts` (`OTP_RATE_LIMITED`, `OTP_EXPIRED`, `OTP_INVALID`, `PHONE_BLOCKED`, `PHONE_NOT_VERIFIED`, `SESSION_INVALID`, `SESSION_REUSE_DETECTED`, ...)؛ فرمت پاسخ خطا `{ code, message, details? }` طبق بند ۵ اسپک، پیاده‌سازی با `AllExceptionsFilter` سراسری
- برای rate limit، هدر `Retry-After` هم ارسال می‌شود

### ۲۴. اندپوینت‌ها (تأیید شده با اجرای زنده روی سرور واقعی)

همه با prefix `/api/v1`: `POST /auth/otp/request`، `POST /auth/otp/verify`، `POST /auth/refresh`، `POST /auth/logout`، `POST /auth/logout-all`، `GET /auth/me`، `PATCH /auth/role`، `POST /auth/ws-ticket` (تیکت یک‌بارمصرف، TTL ۶۰ ثانیه در Redis). `GET /health` عمداً `@Public()` است (برای health-check‌های زیرساخت بدون auth) — این هم یک باگ واقعی بود که موقع اجرای زنده کشف و رفع شد.

### ۲۵. نقش‌ها — `roleIntent` در برابر `SystemRole`

- `roleIntent` (`SEEKER`/`PROVIDER`، از فاز ۲) صرفاً UX است: کاربر با `PATCH /auth/role` آن را عوض می‌کند تا فرم‌ها/فیلترهای مناسب را ببیند؛ **هیچ‌جا برای authorization استفاده نمی‌شود** — کاربر با نقش `SEEKER` هم می‌تواند بعداً پیشنهاد بدهد (رفتار عمداً غیرانحصاری، تست شده)
- `SystemRole` (`USER`/`ADMIN`، فیلد جدید روی `User`) تنها منبع authorization سطح سیستم است؛ گارد `RolesGuard` + دکوریتور `@Roles(...)` (کپی ساختاری از `RequireVerifiedPhoneGuard`: خواندن از DB با کش Redis ۳۰ ثانیه‌ای، بدون invalidation صریح، مثل بند ۲۱) — پیاده‌سازی در `apps/api/src/common/guards/roles.guard.ts` و `common/decorators/roles.decorator.ts`

### ۲۶. `toPublicUser()` — تنها راه خروج داده‌ی کاربر

- تابع واحد `apps/api/src/auth/user-view.ts` تنها مسیر مجاز خروج آبجکت `User` از API است؛ فیلدهای `phone`، `phoneVerifiedAt` خام، `status`، `systemRole` و `avatarStorageKey` هرگز در خروجی ظاهر نمی‌شوند (حتی برای پروفایل خودِ کاربر)
- `phoneVerified: boolean` مشتق از `phoneVerifiedAt !== null` جایگزین timestamp خام شد
- تست خودکار (`user-view.spec.ts` + تست‌های سرویس) ثابت می‌کند شماره‌ی هیچ کاربری، نه فقط کاربران دیگر، در JSON خروجی ظاهر نمی‌شود؛ همچنین با اجرای زنده روی سرور واقعی تأیید شد (بخش پایین)
- قاعده‌ی ESLint سفارشی و type-aware `local/no-raw-user-return` (`eslint-rules/no-raw-user-return.mjs`، متصل در `eslint.config.mjs` فقط روی `apps/api/src/**/*.controller.ts`) به‌عنوان مکانیزم واقعی اجرای این بند اضافه شد — بررسی می‌کند که نوع مقدار `return` هر متد کنترلر (مستقیم یا یک لایه تودرتو در یک آبجکت wrapper مثل `{ user, completeness }`، الگوی واقعی این پروژه) به‌طور ساختاری شامل هر سه فیلد `phone`+`phoneVerifiedAt`+`systemRole` نباشد. با یک کنترلر آزمایشی موقت (حذف‌شده بعد از تأیید) هم حالت مستقیم و هم حالت wrapper شده به‌صورت دستی تأیید شد که خطا می‌دهند، و کنترلرهای واقعی فعلی تمیز پاس می‌شوند.

### ۲۹. دسته‌ها و مهارت‌ها — فقط ادمین‌کیوریت

## تصمیم‌های محصولی معلق

> برخلاف «بدهی فنی» (که چیزی ناقص یا نادرست است)، این بخش تصمیم‌هایی را ثبت می‌کند
> که از نظر فنی هیچ نقصی ندارند — فقط یک انتخاب محصولی هنوز گرفته نشده.

- **Toggle واقعی حالت تاریک (dark mode).** `next-themes` که با نصب `sonner` آمده
  بود، چون هرگز به یک `ThemeProvider` واقعی وصل نشد، کاملاً حذف شد (بازبینی فاز ۴)؛
  `packages/ui/src/components/ui/sonner.tsx` اکنون همیشه `theme="system"` را
  hardcode می‌کند. این یک باگ یا بدهی نیست — تصمیم اینکه اپ اصلاً toggle
  روشن/تاریک داشته باشد یا نه (و اگر بله، با کدام کتابخانه) هنوز گرفته نشده.
  **وضعیت تست کنتراست در همین حالت:** `packages/ui/src/styles/globals.contrast.test.ts`
  واقعاً **هر دو** تم را پوشش می‌دهد — `parseCssCustomProperties(globalsCss, ':root')`
  و `parseCssCustomProperties(globalsCss, '.dark')` هر دو استخراج و در
  `describe.each([['light', ...], ['dark', ...]])` روی همان ۱۰ جفت متن/پس‌زمینه چک
  می‌شوند (۲۰ تست = ۱۰ جفت × ۲ تم، هر ۲۰ تا زنده pass — `npx vitest run
src/styles/globals.contrast.test.ts` در `packages/ui`). این یک ادعای الکی نیست:
  تست دارد مقادیر واقعی توکن‌های `.dark` در `globals.css` را با فرمول WCAG می‌سنجد.
  آنچه پوشش داده **نمی‌شود**، تجربه‌ی زنده‌ی toggle‌شده در مرورگر است — چون اصلاً
  toggleای وجود ندارد که تم را در runtime عوض کند؛ تا وقتی این تصمیم گرفته نشود،
  تست فقط می‌تواند مقادیر CSS را استاتیک بسنجد، نه یک صفحه‌ی واقعاً رندرشده در تاریک.

### باگ‌های واقعی که در اجرای زنده کشف و رفع شدند

این‌ها فقط با اجرای واقعی سرور کشف شدند، نه با تست واحد یا typecheck:

1. **اتصال BullMQ**: `BullModule.registerQueue()` به‌تنهایی کانکشن Redis نمی‌سازد؛ بدون `BullModule.forRootAsync` سراسری (`BullRedisModule` جدید)، برنامه با خطای «Worker requires a connection» بالا نمی‌آمد. رفع شد با یک ماژول سراسری که کانکشن Redis مشترک را برای همه‌ی صف‌های آینده (طبق تصمیم فاز ۰) فراهم می‌کند.
2. **`GET /health` عمداً باید `@Public()` باشد** — گارد سراسری fail-closed آن را هم می‌بست، که برای health-check‌های زیرساخت (بدون auth) اشتباه است. رفع شد.
3. **اجرای dev واقعاً کار نمی‌کرد**: `packages/shared` و `packages/ui` با `moduleResolution: "bundler"` و بدون build نوشته شده‌اند (مناسب برای Next.js/webpack و ts-jest)، ولی این با اجرای مستقیم توسط Node/`nest start`/esbuild سازگار نیست:
   - `nest start` (که به‌صورت داخلی ts-node را با تنظیمات خودش صدا می‌زند، نه CLI استاندارد) با خطای `ERR_UNSUPPORTED_DIR_IMPORT` روی `export * from './utils'` مواجه می‌شد، چون در حالت type-checked، ts-node تنظیمات `moduleResolution: bundler` پکیج shared را resolve می‌کرد که با `--transpile-only` سازگار نیست.
   - `tsx` (esbuild) این مشکل خاص را حل می‌کرد ولی یک مشکل دیگر ایجاد می‌کرد: esbuild به‌درستی decorator metadata مورد نیاز DI نستجی (`design:paramtypes`) را emit نمی‌کند، پس تمام سرویس‌های constructor-injected (مثل `RedisService`) با `undefined` به جای وابستگی واقعی می‌ساختند.
   - راه‌حل نهایی: اسکریپت `dev` به `ts-node --transpile-only -r tsconfig-paths/register src/main.ts` تغییر کرد (نه `nest start`، نه `tsx`) — چون ts-node واقعاً از کامپایلر TypeScript استفاده می‌کند (metadata درست) و `--transpile-only` چک سازگاری `module`/`moduleResolution` بین پروژه‌های تو در تو را رد می‌کند.
4. **Turbo در `envMode: "strict"` اجرا می‌شود** (پیش‌فرض Turborepo 2.x) — متغیرهای محیطی shell (مثل `DATABASE_URL`, `REDIS_URL`, `OTP_PEPPER`) به‌طور پیش‌فرض به تسک‌های فرزند منتقل **نمی‌شوند**، مگر در `globalPassThroughEnv` (یا `env`) در `turbo.json` صراحتاً لیست شوند. بدون این، `pnpm test`/`pnpm lint` از ریشه (نه از داخل `apps/api`) با خطای «Environment variable not found: DATABASE_URL» شکست می‌خورد حتی وقتی متغیر در شل export شده بود. لیست کامل تمام متغیرهای `.env.example` (api + web) به `globalPassThroughEnv` اضافه شد.
5. **Race condition واقعی در turbo**: تسک سراسری `lint` (و `test`) به `^generate` وابسته نبود؛ وقتی `pnpm lint` از ریشه چند پکیج را همزمان اجرا می‌کرد، `@vaqt/db#lint` (که به `generate` وابسته است) گاهی هم‌زمان با `@vaqt/api:lint` اجرا می‌شد — `prisma generate` وسط نوشتن Client، فایل‌های نوع را موقتاً ناقص می‌کرد و eslint نوع‌آگاه apps/api را با ده‌ها خطای «type cannot be resolved» مواجه می‌کرد که هیچ‌کدام واقعی نبودند. رفع شد با اضافه‌کردن `dependsOn: ["^generate"]` به تسک‌های سراسری `lint` و `test` در `turbo.json`.

نسخه‌ی نصب‌شده‌ی `shadcn` (`4.18.0`) فقط CSS مخصوص Tailwind **v4** تولید می‌کند (`@theme inline`, `@custom-variant`) ولی `apps/web` تا این لحظه روی Tailwind **v3.4** بود. این ناسازگاری با خواندن package.json دیده نمی‌شد؛ فقط وقتی خروجی واقعی `globals.css` بررسی شد (شامل at-rule های v4-only) و بعد `next build` روی v3 اجرا شد، مشخص شد که `bg-background`/`border-border`/`outline-ring` هیچ کدام یک utility واقعی تولید نمی‌کنند (چون v3 برای این، نیاز به `theme.colors` صریح دارد، نه یک CSS custom property دلخواه). **تصمیم:** ارتقا به Tailwind v4 (`tailwindcss@^4.3.3` + `@tailwindcss/postcss`، بدون `autoprefixer` که دیگر لازم نیست).

**پنج تأیید زنده روی خروجی کامپایل‌شده‌ی واقعی (۲۰۲۶-۰۸-۲۱، `pnpm --filter @vaqt/web build` با `.next` کاملاً پاک‌شده، سپس `grep` روی `apps/web/.next/static/css/*.css`):**

1. **بدون تصادم `border`/`ring`:** `.border-border{border-color:var(--border)}` (توکن معنایی shadcn) و `.text-brand-900{color:#2e2547}` (رنگ برند، بعد از rename به `brandBorder`) هر دو مستقل و درست کامپایل می‌شوند؛ `outline-ring:focus-visible{outline-color:var(--ring)}` هم حاضر است.
2. **`@theme inline` واقعاً اثر دارد:** خروجی کامپایل‌شده شامل `--color-border:var(--border)` است — یعنی نگاشت semantic-token-به-CSS-var بلوک `@theme inline` در `packages/ui/src/styles/globals.css` واقعاً در CSS نهایی جاری شده، نه فقط در منبع باقی مانده.
3. **`tw-animate-css` بارگذاری شده:** utility های `animate-in`/`animate-out` این پکیج در CSS کامپایل‌شده حضور دارند.
4. **هدف مرورگر مشخص و مستند شد (قبلاً هیچ‌جا ثبت نشده بود):** Tailwind v4 خودش بدون هیچ polyfill به ویژگی‌های مدرن CSS (cascade layers بومی، `@property`، `color-mix()`) متکی است و طبق مستندات رسمی حداقل نسخه‌های Safari 16.4 / Chrome 111 / Firefox 128 را هدف می‌گیرد. این حداقل به‌صورت صریح در `apps/web/package.json` (`"browserslist": ["safari >= 16.4", "chrome >= 111", "firefox >= 128"]`) ثبت شد تا هم مستند باشد و هم ابزارهایی مثل SWC/Next که به `browserslist` نگاه می‌کنند همین هدف را ببینند.
5. **Vazirmatn واقعاً self-host است:** `@font-face{font-family:vazirmatn;src:url(/_next/static/media/41c9fb9084869680-s.p.woff2) format("woff2");font-display:swap}` — مسیر `url()` به یک فایل استاتیک محلی زیر `/_next/static/media/` اشاره می‌کند؛ `grep -c "fonts.googleapis\|fonts.gstatic"` روی همان فایل CSS نتیجه‌ی `0` داد.

### معماری مونوریپو shadcn/ui (تأیید شده با اجرای واقعی CLI، نه فقط خواندن مستندات)

- `packages/ui/package.json` یک فیلد `exports` واقعی گرفت (`./components/*` → `./src/components/*.tsx`, `./lib/*` → `./src/lib/*.ts`, `./hooks/*` → `./src/hooks/*.ts`, `./styles/*` → `./src/styles/*`) — این فیلد صرفاً برای اپ نیست؛ خودِ CLI برای resolve کردن alias های cross-package (`@vaqt/ui/components/ui` و…) دقیقاً از همین exports map استفاده می‌کند (دیدنِ سورس واقعی بسته‌ی نصب‌شده در `node_modules/.pnpm/shadcn@4.18.0.../dist/chunk-2CD4IZV7.js` این را تأیید کرد؛ حدس اولیه بر پایه‌ی docs قدیمی‌تر اشتباه از آب درآمد).
- **هر دو طرف** به `components.json` نیاز دارند: هم `apps/web/components.json` (چون فقط آنجا next.config شناسایی می‌شود و CLI framework را تشخیص می‌دهد) و هم `packages/ui/components.json` (چون CLI هنگام عبور از مرز پکیج، «workspace config» مقصد را هم می‌خواهد؛ بدون آن با خطای صریح شکست می‌خورد). در `apps/web/components.json` تمام aliases (`components`, `ui`, `lib`, `hooks`, `utils`) به `@vaqt/ui/...` تغییر کردند؛ در `packages/ui/components.json` همان مقادیر به‌صورت self-referencing تکرار شدند.
- روش واقعی افزودن کامپوننت (تأیید شده با افزودن واقعی `button`):
  ```
  pnpm --filter @vaqt/ui exec shadcn add <name> -c ../../apps/web -y
  ```
  (نه از `apps/web` — چون بستهٔ `shadcn` فقط dependency خودِ `packages/ui` است، نه `apps/web`.) کامپوننت مستقیماً در `packages/ui/src/components/ui/<name>.tsx` نوشته می‌شود؛ apps/web آن را با `import { X } from '@vaqt/ui/components/ui/x'` مصرف می‌کند (deep import، نه از طریق barrel — همان الگویی که خودِ فایل تولیدشده هم برای `cn` از `@vaqt/ui/lib/utils` استفاده می‌کند).
- `packages/ui/src/index.ts` فقط برای موارد دستی/مشترک (نه کامپوننت‌های تولیدشده‌ی CLI) استفاده می‌شود: `cn` و `DirectionProvider` (از `@radix-ui/react-direction`، re-export شده تا `apps/web` مستقیماً به radix وابسته نباشد).

### RTL

`--rtl` هنگام init پاس داده شد (`"rtl": true` در هر دو `components.json`). این صرفاً metadata تزئینی نیست: کامپوننت تولیدشده‌ی واقعی (`button.tsx`) خودش از یوتیلیتی‌های منطقی Tailwind استفاده می‌کند (`ps-2`/`pe-2`، نه `pl-2`/`pr-2`) — یعنی الزام بند ۱ همین فایل را خودِ رجیستری shadcn هم رعایت می‌کند، بدون نیاز به دست‌کاری دستی. علاوه بر آن، `<DirectionProvider dir="rtl">` در `apps/web/src/app/layout.tsx` کل درخت را می‌پیچد (در کنار `<html dir="rtl">` که از قبل بود).

**رفع بدهی (بسته‌ی بعدی، همین فاز):** قاعده‌ی ESLint سفارشی `local/no-physical-tailwind-classes` نوشته شد (`eslint-rules/no-physical-tailwind-classes.mjs`) — روی هر `Literal`/`TemplateElement` رشته‌ای که در یک attribute با نام `className`/`class` یا در آرگومان فراخوانی `cn`/`clsx`/`cva`/`cx`/`classnames`/`twMerge`/`twJoin`/`tv` قرار دارد، هر token را جدا بررسی می‌کند و `pl-`/`pr-`/`ml-`/`mr-`/`left-`/`right-`/`text-left`/`text-right`/`border-l`/`border-r`/`rounded-l`/`rounded-r`/`float-left`/`float-right`/`clear-left`/`clear-right` (با پیشوندهای variant مثل `md:`/`hover:`/`dark:` و علامت منفی `-ml-2`) را رد می‌کند؛ کلاس‌های واقعی مثل `rounded-lg`/`border-red-500`/`border-rose-200` را با یک lookahead روی مرز token اشتباه نمی‌گیرد (۱۹ تست RuleTester). محدودیت مستند: چون بدون type-info است، مقادیر کاملاً دینامیک (`className={x}`) و CSS دلخواه مثل `[padding-left:10px]` را نمی‌بیند.

- **apps/web از `.eslintrc.json` به `eslint.config.mjs` (flat config) مهاجرت کرد** — نه صرفاً برای این قاعده، بلکه چون `next lint` هم اکنون (خروجی واقعی build) صراحتاً اعلام می‌کند در Next.js 16 حذف می‌شود؛ `next/core-web-vitals`+`next/typescript` با `FlatCompat` از `@eslint/eslintrc` (که به‌عنوان devDependency مستقیم اضافه شد، نه phantom) پل زده شدند. بدون این مهاجرت، قاعده‌ی جدید فقط روی `packages/ui` اثر می‌کرد، نه روی کد واقعی apps/web که بیشترین استفاده‌ی `className` در آن اتفاق می‌افتد.
- در `packages/ui`، قاعده روی `src/**/*.tsx` با `ignores: ['packages/ui/src/components/ui/**']` اعمال شد — چون آن پوشه محصول `shadcn add` است (vendor، نه دست‌نویس) و هر ۱۷ کامپوننت فعلی از قبل روی همین قاعده تست و تأیید سبز شدند.
- تأیید زنده (نه فقط unit test): یک `pl-4` موقت در `apps/web/src/app/page.tsx` تزریق شد، `next lint` واقعاً خطا داد (`Physical Tailwind utility "pl-4" is banned...`)، سپس فایل به حالت اول برگشت و `pnpm lint` دوباره سبز شد.

### دسته‌ی دوم کامپوننت‌ها

با همان دستور (`pnpm --filter @vaqt/ui exec shadcn add <names...> -c ../../apps/web -y`) ۱۶ کامپوننت پایه‌ی دیگر اضافه شد: `card`, `input`, `label`, `textarea`, `select`, `badge`, `avatar`, `dialog`, `dropdown-menu`, `separator`, `tabs`, `skeleton`, `tooltip`, `checkbox`, `switch`, `sonner` — انتخاب‌شده چون فازهای ۵ تا ۹ (فرم درخواست، لیست پیشنهادها، چت، تسویه) همگی به این پرایمیتیوها نیاز دارند.

- کامپوننت `sonner` خودش دو وابستگی جدید (`sonner`, `next-themes`) به `packages/ui` اضافه کرد (به‌صورت خودکار توسط CLI، نه دستی).

### بستن هفت پیش‌نیاز فاز ۴ (بازبینی مجزا، پیش از ادامه‌ی کار طراحی)

هفت مورد پیش‌نیاز صریح فاز ۴ بررسی شد. شش مورد از قبل (در پایان فاز ۳) واقعاً پیاده‌سازی شده بودند؛ با اجرای واقعی (نه فقط خواندن کد) تأیید و بند باز هفتم (شماره‌گذاری برنچ/تگ) تکمیل شد:

1. **جداسازی `toPublicUser`/`toPrivateUser`:** بررسی کد نشان داد این کار از پایان فاز ۳ کامل انجام شده بود (`apps/api/src/auth/user-view.ts`) — دقیقاً طبق اسپک (`maskedPhone`, `phoneVerified: boolean`, `status`, `systemRole`, `completeness`؛ `roleIntent` از قبل روی `PublicUser` پایه بود که `PrivateUser` آن را به ارث می‌برد، همان چیزی که اسپک «intentRole» می‌نامید). قاعده‌ی `local/restrict-to-private-user` هم از قبل call site را به دو فایل مجاز محدود می‌کرد. چیزی برای تغییر نبود؛ فقط با اجرای `pnpm test` واقعی دوباره تأیید شد.
2. **CI:** workflow از قبل وجود داشت (Postgres 16 + Redis 7 service container، `migrate deploy`، سپس lint/typecheck/build/test) ولی **هرگز روی GitHub واقعاً اجرا نشده بود** (هیچ run ثبت‌شده‌ای نبود، چون commit حاوی آن هنوز push نشده بود). با push کردن، یک باگ واقعی کشف شد (به‌پایین مراجعه شود) و پس از رفع آن، CI روی یک checkout کاملاً تازه سبز شد.
3. **`master` → `main` + تگ‌های annotated:** برنچ پیش‌فرض با `gh api` به `main` تغییر کرد (بعد از push کردن و set‌کردن upstream)، `master` قدیمی از remote حذف شد. هر سه تگ فاز (`phase-0`, `phase-1`, `phase-2`) که lightweight بودند، حذف و با همان پیام کامیت و روی همان commit SHA به‌صورت annotated (`git tag -a`) بازسازی و دوباره push شدند (تأیید شد با `git for-each-ref --format='%(objecttype)'`: هر سه اکنون `tag` هستند، نه `commit`). سپس branch protection روی `main` با `required_status_checks.contexts: ["ci"]` + `enforce_admins: true` + `allow_force_pushes/deletions: false` فعال شد.
4. **تست دائمی قواعد ESLint:** از قبل کامل بود — `no-raw-user-return.test.mjs` (۴ تست، شامل حالت مستقیم، wrapper، و یک تست regression برای `PrivateUser` که نباید false-positive بدهد) و `restrict-to-private-user.test.mjs` (۵ تست). تنها مشکل این بود که این‌ها با یک اسکریپت جدا (`test:eslint-rules`) اجرا می‌شدند، نه از داخل `turbo run test` — رفع آن در بند بعد.
5. **بدهی `packages/shared`/`packages/db`:** از قبل رفع شده بود (تسق tsup، `dist` با CJS+ESM+d.ts، `apps/api` روی `nest start --watch`). برای `packages/ui` **عمداً همان کار انجام نشد** — تصمیم صریح کاربر: مشکلی که shared/db را مجبور به build کرد یک باگ واقعی بود (ts-node/esbuild در NestJS متادیتای decorator را درست emit نمی‌کرد)؛ `packages/ui` فقط توسط Next.js مصرف می‌شود که خودش TSX منبع را از workspace packages درست transpile می‌کند (در همین فاز ۴ با build واقعی اثبات شد)، پس آن باگ اصلاً وجود ندارد. Build کردن `packages/ui` با tsup هزینه‌ی واقعی داشت (حفظ `"use client"`, باندل CSS Tailwind، externalize کردن react) بدون رفع هیچ باگی، و با گردش‌کار خودِ `shadcn add` (که مستقیم در `packages/ui/src` می‌نویسد) در تضاد بود. **تصمیم نهایی: `packages/ui` عمداً source-only باقی می‌ماند** (`main: ./src/index.ts`، مصرف مستقیم TSX از طریق نگاشت `exports`)، برخلاف `shared`/`db` که به `dist` بیلد می‌شوند — این عدم‌تقارن آگاهانه است، نه بدهی فراموش‌شده.
   **قاعده‌ی مصرف پکیج‌ها (build شده در برابر source-only) — اثبات زنده، ۲۰۲۶-۰۸-۲۱:**

- `apps/web/next.config.ts` دارای `transpilePackages: ['@vaqt/ui', '@vaqt/shared']` است — یعنی Next.js صراحتاً هر دو را از TSX/TS منبع transpile می‌کند، نه از `dist`.

### دو باگ واقعی که فقط با اجرای زنده (curl روی سرور واقعی) کشف شدند

هیچ‌کدام با تست واحد/typecheck/lint قابل کشف نبودند — چون **هیچ تستی در کل این ریپو، برای
هیچ کنترلری، بوت واقعی از طریق `main.ts` را با HTTP واقعی امتحان نمی‌کند** (کنترلر-تست‌های
موجود مثل `users.controller.spec.ts` مستقیماً متد کلاس را صدا می‌زنند، بدون عبور از هیچ
Guard/Pipe/Filter واقعی). این خودش یک شکاف تست است، ثبت‌شده به‌عنوان درسِ این بازبینی، نه یک
بدهی جدید در جدول (چون رفع آن — افزودن یک لایه‌ی تست e2e واقعی — فراتر از scope این PR است).

1. **`app.useGlobalPipes(new ValidationPipe({whitelist, forbidNonWhitelisted}))` در `main.ts`
   هر روت مبتنی‌بر zod را می‌شکست.** این کلاس-validator pipe سراسری بود، در حالی که
   `CreateRequestDto`/`UpdateUserProfileDto`/... (همه‌ی DTOهای فاز ۳ به بعد) هیچ دکوریتور
   class-validator ندارند (طبق تصمیم مستند در همین فایل: «schema-اول... نه مانی‌فست global»).
   با `whitelist:true`، هر فیلد بدون دکوریتور class-validator "ناشناخته" تلقی و حذف می‌شود؛
   با `forbidNonWhitelisted:true` همان حذف باعث 400 می‌شود. یعنی از فاز ۳ به بعد، **هیچ
   اندپوینت zod-محور این پروژه هرگز واقعاً روی سرور بوت‌شده کار نمی‌کرد** — فقط چون هیچ‌کس
   قبلاً curl واقعی روی آن‌ها نزده بود، کشف نشده بود. تنها `AuthController` واقعاً به این
   pipe سراسری نیاز داشت (سه DTO قدیمی‌تر از فاز ۲: `RequestOtpDto`/`VerifyOtpDto`/`UpdateRoleDto`
   هنوز class-validator هستند). رفع: `useGlobalPipes` از `main.ts` حذف شد؛
   `@UsePipes(new ValidationPipe(...))` به‌جایش روی خودِ کلاس `AuthController` گذاشته شد
   (scope شد، نه حذف رفتار). تأیید زنده: `PATCH /users/me` بعد از رفع، واقعاً به Prisma رسید
   (قبلش هرگز نمی‌رسید).
2. **`@UsePipes()` سطح متد وقتی هم `@CurrentUser()` هم `@Body()` در یک متد باشند، pipe را
   روی هر دو پارامتر resolve‌شده اجرا می‌کند، نه فقط `@Body()`.** `create()` این ترکیب را
   داشت؛ `publish()`/`list()` فقط `@Body()` داشتند و به همین دلیل این باگ را نشان نمی‌دادند.
   نتیجه‌ی مشاهده‌شده: بدنه‌ی واقعی curl (که در سطح Guard با `console.error` موقت تأیید شد
   کاملاً درست می‌رسد) وقتی به Pipe می‌رسید، انگار کاملاً خالی بود — هر فیلد «Required»،
   دقیقاً مثل تست دستی pipe با ورودی `{}`. رفع: `ZodValidationPipe` از سطح متد
   (`@UsePipes`) به سطح پارامتر منتقل شد (`@Body(new ZodValidationPipe(CreateRequestDto))`)
   برای هر سه اندپوینت (برای یکدستی، نه فقط `create` که واقعاً می‌شکست).

**نکته‌ی جانبی، هنگام دیباگ کشف شد، عمداً در همین PR رفع نشد ولی به جدول «بدهی فنی» اضافه
شد (ردیف چهارم جدید):** `AllExceptionsFilter` برای هر `HttpException` غیر-`AppError` (نه فقط
خطاهای اعتبارسنجی واقعی) کد را بی‌قیدوشرط `VALIDATION_ERROR` می‌گذارد و فقط `body.message`

در `/requests`، بدون auth). این PR سه جریان کامل مرورگری را متصل می‌کند: ورود با OTP،

بک‌اند واقعی موجود، بدون هیچ تغییری در apps/api به‌جز مستندسازی باگی که در حین این کار
کشف شد (پایین).

### تصمیم توکن/Session: httpOnly Cookie

بک‌اند از قبل کاملاً حول کوکی httpOnly ساخته شده بود (بند ۲۰-۲۱)؛ این تصمیم تطابق با
معماری موجود است، نه یک انتخاب جدید. دلیل امنیتی: httpOnly یعنی جاوااسکریپت اصلاً به
توکن دسترسی ندارد — سرقت توکن از طریق XSS (رایج‌ترین بردار حمله در SPA) عملاً غیرممکن
می‌شود؛ localStorage کاملاً در معرض هر اسکریپت تزریق‌شده است. `apps/web/src/lib/api-client.ts`
یک fetch wrapper نازک است (`credentials:'include'`, بدون هیچ token store)؛ روی ۴۰۱ یک‌بار
`POST /auth/refresh` را امتحان می‌کند و retry می‌زند؛ اگر خودِ refresh هم ۴۰۱ بدهد،
مستقیم `window.location.href = '/login'` می‌زند (بدون retry حلقه‌ای). یک flag
(`redirectOnAuthFailure`) این رفتار را برای چک اولیه‌ی `GET /auth/me` در `auth-context.tsx`
خاموش می‌کند — وگرنه هر بازدیدکننده‌ی مهمان با بارگذاری صفحه‌ی اصلی بلافاصله به `/login`
پرتاب می‌شد (این را حین طراحی، قبل از نوشتن کد، پیدا کردم، نه با دیباگ بعدی).

### باگ واقعی کشف‌شده در apps/web (نه apps/api)

جزئیات کامل با دستور و خروجی خام در جدول «تأییدهای زنده» بالا. خلاصه: `apps/web/src/app/requests/page.tsx`
نسخه‌ی Server Component هرگز واقعاً کار نمی‌کرد — میدل‌ور `origin-check` بک‌اند (که هر
`POST` را mutating می‌داند، حتی وقتی معنایی list/read باشد) بدون هدر `Origin` مطابق
`WEB_ORIGIN` را ۴۰۳ می‌کند، و `fetch` سمت سرور Next.js (Node) هرگز این هدر را نمی‌سازد.
کامپوننت هم `!res.ok` را بی‌صدا به یک پیام خطای عمومی تبدیل می‌کرد — یعنی این صفحه از
زمان merge شدن (PR ۱) همیشه حالت خطا نشان می‌داد، نه لیست واقعی، و چون تست‌های PR ۱ با
`curl` دستی (Origin صریح) انجام شده بودند نه با رندر واقعی صفحه، کشف نشده بود. رفع: خودِ
`origin-check.middleware.ts` دست‌نخورده ماند (طبق دستور صریح: تغییری در بک‌اند نه)؛ صفحه
به Client Component تبدیل شد تا fetch واقعاً از مرورگر برود (Origin خودکار توسط مرورگر
ست می‌شود) — همین تغییر هم باگ را رفع کرد و هم امکان «بارگذاری بیشتر» کرسر-محور تعاملی
واقعی را داد (چیزی که یک Server Component اصلاً نمی‌تواند بدهد).

### اعتبارسنجی فرم ساخت درخواست

فرم `request-form.tsx` مستقیماً از `createRequestSchema` واقعی `@vaqt/shared` استفاده
می‌کند — نه یک بازنویسی موازی. یک schema کمکی محلی (`rawFormSchema`) فقط شکل خام ورودی
مرورگر (رشته‌ها) را با `zodResolver` می‌گیرد و فیلدهای خالی را زودتر نشان می‌دهد، بدون
هیچ قاعده‌ی کسب‌وکاری تکراری (بدون min/max عنوان، بدون بازه‌ی بودجه و…)؛ تصمیم واقعیِ
معتبر/نامعتبر همیشه با `createRequestSchema.safeParse()` روی داده‌ی تبدیل‌شده (تومان
کاربر → ریال با `tomanToRial()` از `@vaqt/shared`) گرفته می‌شود، و خطاهای هر فیلد با یک
جدول نگاشت (`SCHEMA_TO_FORM_FIELD`) به نام فیلد فرم برمی‌گردند. خطای سرور (که فعلاً به
دلیل بدهی فنی شناخته‌شده‌ی `AllExceptionsFilter` فقط پیام کلی می‌دهد، نه per-field) فقط
به‌عنوان یک banner عمومی نمایش داده می‌شود — طبق تصمیم محصولی صریح، نه فرض.

### جریان publish دومرحله‌ای

طبق تصمیم محصولی صریح: بعد از `POST /requests` (ساخت DRAFT)، فرم به یک پیش‌نمایش تبدیل
می‌شود (بدون navigation — همان state کامپوننت) با دکمه‌ی صریح «انتشار»؛ auto-publish
پیاده نشد. کلیک «انتشار» → `POST /requests/publish` → موفق → `redirect` به `/requests`.

### اثبات زنده (E2E کامل، Postgres/Redis واقعی، بدون mock به‌جز `SMS_PROVIDER=mock`)

با یک شماره‌ی تصادفی تازه (برای پرهیز از rate-limit واقعی Redis روی شماره‌های استفاده‌شده‌ی
قبلی — طبق هشدار صریح، فرض نشد که همیشه پاس می‌شود)، جریان هفت‌مرحله‌ای کامل روی API واقعی:

1. `POST /auth/otp/request` → `{"ok":true,"expiresIn":120,"resendAfter":60}`؛ کد از لاگ
   واقعی `MockSmsAdapter` خوانده شد (`[mock-sms] OTP for +98988***2054: 11928`)
2. `POST /auth/otp/verify` → کوکی‌های httpOnly صحیح (`access_token`, `refresh_token`) +
   `phoneVerified:true`, `completeness.canPublishRequest:true`
3. `GET /auth/me` با همان کوکی → `200 OK`
4. `GET /categories` → دسته‌ی واقعی (`cat-web-dev`) برای مرحله‌ی بعد
5. `POST /requests` → `{"id":"...","status":"DRAFT"}`
6. `POST /requests/publish` → `{"id":"...","status":"PUBLISHED","publishedAt":"..."}`
7. `POST /requests/list` **بدون هیچ کوکی** (دیدگاه مهمان) → درخواست تازه در فهرست عمومی
   دیده شد، با `budgetMinRial: null, budgetMaxRial: null` (بدون نشتی بودجه، طبق بند ۶)

پاک‌سازی: `request`/`session`/`verification_code`/`user` تستی مستقیماً از Postgres واقعی
حذف شدند؛ شمارش نهایی seed تأیید شد بدون تغییر ماند (۸ کاربر، ۱۵ درخواست).

## یادداشت‌های فاز فعلی (فاز ۵ / PR ۳) — فیلد UI برای preferredWindows

### مشکلی که این PR رفع کرد

از زمان نوشتن `createRequestSchema` (بند «۱۵. مهارت‌های درخواست» بالا اشاره‌ای ندارد،
ولی خودِ اسکیمای `packages/shared/src/schemas/request.ts` از ابتدا) فیلد `preferredWindows`
(آرایه‌ای از `{day, start, end}` با regex زمان `HH:mm`) وجود داشت، ولی فرم واقعی
(`request-form.tsx`) همیشه `preferredWindows: []` هاردکد می‌فرستاد — یعنی این بخش از
schema هرگز از طریق UI قابل‌رسیدن نبود، فقط با تست واحد مستقیم روی خودِ schema پوشش
داشت. کشف شد در یک بررسی سریع (بدون تغییر کد) که کاربر درخواست داد.

### تغییر

`RequestForm` اکنون یک بخش تکرارشونده (`useFieldArray`) برای افزودن/حذف ردیف‌های
day/start/end دارد (حداکثر ۲۰ ردیف، مطابق `.max(20)` در schema). فیلدها عمداً
`<input type="text">` ساده هستند، نه `<input type="time">` — چون ورودی native زمان
مرورگر همیشه فرمت معتبر تولید می‌کند و مسیر خطای واقعی regex هرگز قابل‌مشاهده
نمی‌شد. ردیفی که کاملاً خالی رها شود (هر سه فیلد trim-شده خالی) پیش از ارسال حذف
می‌شود — یعنی افزودن یک ردیف خالی، خطای اعتبارسنجی تولید نمی‌کند، فقط پرکردن
ناقص آن (مثلاً فقط day) خطای واقعی نشان می‌دهد. حلقه‌ی نگاشت خطای `handleCreate`
برای مسیرهای تودرتوی `['preferredWindows', index, field]` (که schema واقعاً همین
شکل را برمی‌گرداند) جداگانه هندل شد تا خطا روی ردیف/فیلد درست بنشیند، نه فقط
به‌عنوان یک پیام عمومی.

### اثبات (سه لایه، نه فقط build/typecheck)

۱. اجرای مستقیم `createRequestSchema` واقعی (از `packages/shared/dist`) با
`start: '6pm'` → خطا دقیقاً در مسیر `['preferredWindows', 0, 'start']` با پیام
«باید به شکل HH:mm باشد» — همان مسیری که کد نگاشت خطای فرم انتظار دارد.
۲. اجرای زنده روی سرور واقعی (Postgres/Redis واقعی، جریان کامل OTP→session):

- `POST /requests` با `preferredWindows: [{"day":"شنبه","start":"18:00","end":"20:00"}]`
  → `201 {"id":"...","status":"DRAFT"}`؛ تأیید شد مستقیماً از Postgres
  (`SELECT ... FROM requests`) که مقدار JSON دقیقاً همان آرایه است.
- `POST /requests` با `start: "6pm"` → `400 {"code":"VALIDATION_ERROR",...}`
  (پیام فعلاً عمومی است، نه per-field — همان بدهی فنی شناخته‌شده‌ی
  `AllExceptionsFilter`، بدون تغییر در این PR).
- پاک‌سازی کامل بعد از تست: شمارش نهایی ۸ کاربر / ۱۵ درخواست، بدون تغییر.
  ۳. `pnpm --filter @vaqt/web typecheck/lint/build` سبز؛ `pnpm test` با env واقعی
  صادرشده: ۸/۸ تسک، ۲۸۴/۲۸۴ تست apps/api سبز (بدون رگرسیون؛ این PR هیچ کد
  apps/api را تغییر نداد).

## فاز ۶ — پیشنهادها (Offers)

**چیستی:** ارائه‌دهنده روی یک درخواست PUBLISHED پیشنهاد (زمان پیشنهادی، مدت، مبلغ
ریالی، پیام اختیاری) ثبت می‌کند؛ صاحب درخواست پیشنهادهای دریافتی را می‌بیند و یکی
را انتخاب می‌کند؛ انتخاب به‌صورت اتمیک وضعیت درخواست را `OFFER_SELECTED` می‌کند و
یک `Conversation` می‌سازد (طبق schema فاز ۱ که از قبل `Conversation.offerId`
یکتا دارد). ارائه‌دهنده می‌تواند پیشنهاد `PENDING` خودش را پس بگیرد
(`WITHDRAWN`)، و طبق بند ۱۴ همین فایل، ارسال مجدد بعد از `WITHDRAWN` همان ردیف
را با `revisionCount++` به `PENDING` برمی‌گرداند به‌جای ساخت ردیف جدید.

**چرا این فاز و چرا حالا:** مدل‌های `Offer`/`Conversation`/`Message` از فاز ۱
کامل در schema هستند ولی هیچ endpoint‌ای برایشان نوشته نشده — یعنی درخواست‌های
منتشرشده‌ی فاز ۵ فعلاً یک بن‌بست‌اند، هیچ ارائه‌دهنده‌ای راهی برای پاسخ ندارد. این
اولین حلقه‌ی واقعی دوطرفه‌ی بازار است و مستقیماً روی کاری که در فاز ۵ ساخته شد
سوار می‌شود (بدون نیاز به هیچ مدل/migration جدید). به تصمیم خودمختار در «یادداشت
شماره‌گذاری (۲)» بالا مراجعه شود برای اینکه چرا این فاز به AI (فاز قدیمی ۶)
اولویت داده شد.

**محدوده‌ی تقریبی (ممکن است طی پیاده‌سازی به چند PR برش بخورد، دقیقاً مثل فاز ۵):**
بک‌اند (`apps/api/src/offers/`: ثبت، لیست پیشنهادهای یک درخواست برای صاحبش،
انتخاب، withdraw/resubmit — همه پشت `RequireVerifiedPhone`/`RequireOwnership`
و گیت `computeProfileCompleteness().canSubmitOffer` موجود در
`packages/shared`)، سپس UI صفحه‌ی جزئیات درخواست در `apps/web` برای دیدن/ثبت/
انتخاب پیشنهاد. تصمیم‌های ریز (شکل دقیق DTOها، متن پیام‌های فارسی، تقسیم PR) طبق
مجوز کار خودکار بالا بدون توقف گرفته می‌شوند و همین‌جا مستند می‌مانند.

### تصمیم‌های طراحی گرفته‌شده پیش از شروع کد (مستند برای اینکه بعداً «چرا اینطور شد» گم نشود)

- **گیت ارسال پیشنهاد = `canSubmitOffer` موجود، نه یک قاعده‌ی جدید.** تابع
  `computeProfileCompleteness` (فاز ۳) از قبل تعریف می‌کند که ارسال پیشنهاد نیاز
  به `displayName`+`bio`+حداقل یک مهارت دارد — **نه** تأیید شماره موبایل (برخلاف
  انتشار درخواست که هم نیاز دارد). این عمداً یک قاعده‌ی از پیش موجود و تست‌شده است؛
  در این فاز بازتعریف نشد، فقط سمت سرور در `OffersService.submit` اجرا می‌شود
  (هرگز به ادعای کلاینت اعتماد نمی‌شود).
- **رفتار resubmit فقط برای `WITHDRAWN` تعریف شده (بند ۱۴)؛ سایر وضعیت‌های
  غیر-`WITHDRAWN` موجود (`PENDING`/`SELECTED`/`REJECTED`/`EXPIRED`) باعث خطای
  `OFFER_ALREADY_EXISTS` می‌شوند**، نه reactivate خاموش — چون بند ۱۴ فقط
  `WITHDRAWN` را صراحتاً «رفتار re-submit» می‌نامد و رفتار برای بقیه مشخص نشده؛
  این کوچک‌ترین تفسیر امن است (رد کردن به‌جای حدس زدن یک قاعده‌ی جدید).
- **انتخاب یک پیشنهاد، سایر پیشنهادهای `PENDING` همان درخواست را `REJECTED`
  می‌کند** (تصمیم محصولی implicit، مستند اینجا): وقتی درخواست به `OFFER_SELECTED`
  می‌رود، دیگر پذیرفتن پیشنهاد دیگری معنا ندارد؛ رد خودکار به‌جای رها کردنشان در
  `PENDING` برای اینکه ارائه‌دهندگان دیگر UI روشنی از نتیجه ببینند.
- **بدون endpoint عمومی «لیست پیشنهادهای یک درخواست»** — فقط صاحب درخواست
  (`RequireOwnership`) می‌تواند پیشنهادهای دریافتی را ببیند؛ ارائه‌دهنده پیشنهاد
  خودش را از طریق پاسخ همان `POST /offers` و یک endpoint جدا («پیشنهادهای من»)
  می‌بیند، نه از لیست عمومی درخواست.

### PR ۱ — بک‌اند Offers (تکمیل‌شده)

`apps/api/src/offers/**` (کنترلر + سرویس + ۴ DTO) + schema مشترک جدید
(`packages/shared/src/schemas/offer.ts`). اندپوینت‌ها همه RPC-style (`@Post`)،
مطابق قاعده‌ی موجود در `RequestsController`:

- `POST /offers` — ثبت پیشنهاد (بدون گارد `RequireVerifiedPhone`، طبق تصمیم
  بالا؛ گیت واقعی `canSubmitOffer` داخل سرویس است)
- `POST /offers/select` — انتخاب، پشت `RequireOwnership` (مالک درخواست)
- `POST /offers/withdraw` — پس‌گیری، پشت `RequireOwnership` (ارائه‌دهنده‌ی همان پیشنهاد)
- `POST /offers/list` — لیست پیشنهادهای یک درخواست، پشت `RequireOwnership` (مالک درخواست)
- `POST /offers/mine` — پیشنهادهای خودِ کاربر واردشده، بدون ownership resolver

**تست:** ۱۷ تست جدید در `offers.service.spec.ts` روی Postgres واقعی (بدون mock)،
پوشش‌دهنده‌ی هر مسیر تصمیم بالا (رد/تکمیل پروفایل، مالکیت خودِ درخواست، وضعیت
درخواست، unique+resubmit، رد خودکار پیشنهادهای رقیب، ساخت Conversation+پیام
سیستمی). `offers.service.ts` پوشش ۹۸٫۲۴٪ statements (تنها خط پوشش‌نیافته، گارد
دفاعی «کاربر توکن‌دار در DB پیدا نشد»، دقیقاً هم‌الگو با خط مشابه در
`users.service.ts` که از قبل هم پوشش نداشت — نه یک نقص جدید).
`public-routes.spec.ts` به‌روزرسانی شد (`OffersController` به لیست کنترلرها
اضافه شد؛ هیچ روت `@Public()` جدیدی نیست).

**اثبات زنده (E2E کامل، Postgres/Redis واقعی):** دو کاربر واقعی (seeker +
provider) با OTP واقعی لاگین شدند؛ پروفایل provider با `PATCH /users/me` +
`PUT /users/me/skills` تکمیل شد (بیوگرافی + یک مهارت واقعی از `GET /skills`)؛
seeker یک درخواست ساخت و منتشر کرد؛ provider با `POST /offers` پیشنهاد ثبت
کرد (`201 PENDING`)؛ seeker با `POST /offers/list` پیشنهاد را دید؛ provider
با همان endpoint امتحان کرد و `403 FORBIDDEN` گرفت (اثبات زنده‌ی
`RequireOwnership`)؛ provider با `POST /offers/mine` پیشنهاد خودش را دید؛
seeker با `POST /offers/select` پیشنهاد را انتخاب کرد. تأیید مستقیم از
Postgres: `requests.status = OFFER_SELECTED`، `offers.status = SELECTED`،
یک ردیف `conversations` واقعی با `seekerId`/`providerId` درست، و یک پیام
`SYSTEM` («این گفتگو به‌دلیل انتخاب پیشنهاد شما آغاز شد.») داخل آن. تمام
داده‌ی تستی بعداً پاک شد؛ شمارش نهایی seed بدون تغییر ماند (۸ کاربر، ۱۵
درخواست، ۲۰ پیشنهاد، ۲ گفتگو).

**باقی‌مانده برای فاز ۶:** UI صفحه‌ی جزئیات درخواست در `apps/web` (دیدن/ثبت/
انتخاب/پس‌گیری پیشنهاد) — یک PR جدا، مطابق الگوی فاز ۵.

### PR ۲ — صفحه‌ی جزئیات درخواست + UI پیشنهادها (تکمیل‌شده)

**چرا این فاز و چرا حالا:** به «یادداشت شماره‌گذاری (۳)» بالا مراجعه شود —
دقیقاً همان استدلالی که Offers را جلوتر از AI برد، اینجا هم صدق می‌کند.

### تصمیم‌های طراحی گرفته‌شده پیش از شروع کد

- **`RequireOwnership` تعمیم داده شد تا آرایه‌ای از owner idها بپذیرد.**
  گفتگو برخلاف Offer/Request دو مالک قانونی دارد (seeker و provider)، ولی
  resolver قبلی فقط یک id برمی‌گرداند. تصمیم: به‌جای دور زدن گارد موجود برای
  این یک مورد، خودِ `OwnershipResolver`/`RequireOwnershipGuard` تعمیم داده
  شد (`string | string[] | null`) — سازگار با عقب، همه‌ی resolverهای فعلی
  (offers, requests) بدون تغییر کار می‌کنند. تست‌های جدید (`allows when the
authenticated user is one of several resolved owners` و مورد رد آن) به
  `require-ownership.guard.spec.ts` اضافه شدند.
- **`GET /conversations/:id` با path param، نه query param.** طبق همان
  دلیل مستندشده برای `GET /requests/:id`/`GET /users/:id`: این دو مورد
  قبلاً از قاعده‌ی ایدئال «بدون path param» در `API_DESIGN.md` عمداً منحرف
  شده‌اند و پیشینه‌ی واقعی این کدبیس همین است، نه سند ایدئال؛ پیروی از
  پیشینه‌ی واقعی برای یکدستی ترجیح داده شد.
- **مشاهده‌ی پیام‌ها، پیام‌های طرف مقابل را به‌عنوان اثر جانبی «خوانده‌شده»
  می‌کند — بدون هیچ سیستم اعلان/badge شمارش نخوانده.** فیلد `Message.readAt`
  از فاز ۱ در schema بود ولی هیچ‌جا نوشته نمی‌شد. تصمیم: `listMessages()`
  فقط پیام‌های طرف مقابل (نه پیام‌های خودِ کاربر، نه پیام SYSTEM با
  `senderId: null`) را که هنوز `readAt: null` دارند، در همان کوئری
  `readAt` می‌کند. این عمداً یک قابلیت مستقل «علامت‌گذاری خواندن» یا سیستم
  اعلان نیست — طبق حد صریح تعیین‌شده توسط کاربر («توقف کن اگه به تصمیم
  محصولی مثل notification رسیدی»)، هیچ شمارنده‌ی نخوانده یا badge ساخته
  نشد؛ فقط یک فیلد از پیش موجود در schema که تا امروز بلااستفاده بود، حالا
  به‌عنوان نتیجه‌ی طبیعی دیدن پیام پر می‌شود.
- **صفحه‌بندی پیام‌ها با همان الگوی cursor نسل‌جدید-اول درخواست‌ها**
  (`createdAt DESC, id DESC`) — نه یک الگوی تازه. کلاینت وب صفحه را برای
  نمایش thread قدیم-به-جدید معکوس می‌کند؛ «بارگذاری بیشتر» عمیق‌تر به عقب
  می‌رود.
- **`OffersService.select()` اکنون `lastMessageAt` را همزمان با ساخت
  Conversation صریحاً ست می‌کند** (قبلاً `null` می‌ماند تا اولین پیام واقعی).
  یک تغییر یک‌خطی در کد از قبل merge‌شده‌ی فاز ۶، چون
  `ConversationsService.listMine()` روی `ORDER BY lastMessageAt DESC`
  مرتب می‌کند و بدون این، گفتگوهای تازه‌ساز تا اولین پیام واقعی در انتهای
  فهرست می‌افتادند.
- **بدون endpoint عمومی «آرشیو کردن گفتگو»** — enum `ConversationStatus`
  از فاز ۱ مقدار `ARCHIVED` دارد و `sendMessage()` آن را رد می‌کند
  (`CONVERSATION_ARCHIVED`)، ولی هیچ مسیری برای رسیدن به آن وضعیت هنوز
  وجود ندارد؛ این یک گارد دفاعی برای وقتی است که آن endpoint در فازی بعدی
  اضافه شود.

  هیچ کلاس فیزیکی `text-left`/`pl-`/`pr-`). این ممکن است با قرارداد رایج
  اپ‌های چت فارسی (پیام خودم همیشه راست) متفاوت به‌نظر برسد — یک تصمیم
  آگاهانه برای یکدستی با بقیه‌ی کدبیس، نه سهل‌انگاری؛ اگر بعداً تصمیم
  گرفته شد برخلاف این قاعده باشد، یک تغییر یک‌خطی (`justify-end` ثابت
  به‌جای شرطی) کافی است.
- **بدون polling یا هیچ به‌روزرسانی خودکار** — چون Socket.IO هنوز ساخته
  نشده، دیدن پیام تازه‌ی طرف مقابل فقط با رفرش صفحه ممکن است؛ این عمداً
  به PR بعدی (real-time) موکول شد، نه یک نقص فراموش‌شده.
- **صفحه‌ی thread پیام‌ها را oldest-to-newest نمایش می‌دهد** — کلاینت
  صفحه‌ی newest-first بک‌اند را reverse می‌کند؛ «بارگذاری قدیمی‌تر» صفحه‌ی
  بعدی را می‌گیرد و به ابتدای آرایه‌ی نمایش prepend می‌کند.

**اثبات زنده (Playwright headless، دو `BrowserContext` مستقل، Postgres/
Redis واقعی، هیچ mock به‌جز `SMS_PROVIDER=mock`):** جریان کامل seeker (A)

- provider (B) از طریق UI واقعی مرورگر (نه curl): A با OTP واقعی وارد شد،
  درخواست ساخت و منتشر کرد (id از پاسخ شبکه‌ی واقعی گرفته شد، نه scrape
  فهرست — چون فهرست عمومی بر اساس `listTier` مرتب می‌شود و درخواست تازه
  لزوماً اول نیست)؛ B با پروفایل تکمیل‌شده (bio+مهارت، از طریق API) پیشنهاد
  داد؛ A از UI واقعی صفحه‌ی جزئیات پیشنهاد را انتخاب کرد → گفتگوی واقعی
  ساخته شد؛ A فهرست گفتگوهایش را باز کرد، وارد thread شد، پیام فرستاد؛ B
  همان گفتگو را باز کرد، پیام A را دید، پاسخ داد؛ A صفحه را رفرش کرد و پاسخ
  B را دید. اسکرین‌شات نهایی صف پیام‌ها (سیستم + دو پیام متنی با ترازبندی
  درست هر طرف) گرفته و بازبینی بصری شد. تنها خطاهای کنسول، همان دو ۴۰۱
  مورد‌انتظار `GET /auth/me` قبل از لاگین در هر context بودند (الگوی
  مستندشده‌ی موجود، نه باگ تازه).

**پاک‌سازی داده‌ی تست — شامل یک نکته‌ی مهم:** سه اجرای اول اسکریپت
Playwright (پیش از رفع باگ‌های انتخابگر) کرش کردند ولی قبل از کرش، داده‌ی
واقعی در Postgres ساخته بودند؛ چون فهرست عمومی بر اساس `listTier` (نه
صرفاً تازگی) مرتب می‌شود، یکی از این اجراهای ناقص با انتخاب اشتباهِ اولین
لینک از فهرست، **یک Offer واقعی روی یک درخواست seed واقعی
(`req-python-consult`)** ثبت کرده بود — نه فقط رکوردهای تستی ایزوله.
پاک‌سازی نهایی: حذف آن Offer به‌همراه `decrement` دستی
`offerCount` همان درخواست seed (تأیید شد قبل/بعد: ۱ → ۰، دقیقاً معادل
همان یک افزایش ناخواسته)، به‌علاوه‌ی حذف ۵ کاربر و ۲ درخواست تستی
باقی‌مانده از اجراهای ناموفق. شمارش نهایی seed با `EXPLAIN`-سطح دقت
تأیید شد که بدون تغییر ماند: ۸ کاربر، ۱۵ درخواست، ۱۲ دسته، ۱۲ مهارت، ۲۰
پیشنهاد، ۲ گفتگو.

`pnpm --filter @vaqt/web typecheck`/`lint`/`build` سبز (بودجه‌ی باندل
سبز؛ `/conversations` و `/conversations/[id]` به‌درستی رندر می‌شوند).

### PR ۳ — Socket.IO gateway (تحویل بی‌درنگ پیام، تکمیل‌شده)

آخرین بخش فاز ۸. اولین استفاده‌ی این پروژه از WebSocket — بدون هیچ
پیشینه‌ی معماری قبلی برای الگوبرداری، پس تصمیم‌های زیر از صفر گرفته شدند
(و اینجا مستند می‌مانند تا فازهای بعدی که به real-time نیاز دارند از همین
الگو پیروی کنند، نه یک الگوی تازه بسازند).

**وابستگی‌های جدید:** `@nestjs/websockets`, `@nestjs/platform-socket.io`,
`socket.io` (نسخه‌ی هم‌راستا با `@nestjs/core@^10.4.15` فعلی)، و
`socket.io-client` فقط برای تست.

**تصمیم‌های طراحی:**

- **REST همچنان تنها مسیر نوشتن است.** `apps/api/src/conversations/
conversations.gateway.ts` هیچ پیامی را مستقیماً از طریق socket
  نمی‌پذیرد یا ذخیره نمی‌کند — فقط اتصال را احراز هویت می‌کند، عضویت در
  room را به مشارکت‌کنندگان واقعی محدود می‌کند، و آنچه
  `ConversationsService.sendMessage()` از قبل persist کرده را
  دوباره‌پخش (broadcast) می‌کند. یعنی تمام اعتبارسنجی/گاردهای موجود
  (`CONVERSATION_ARCHIVED`, ownership) بدون تغییر و بدون تکرار منطق
  همچنان اعمال می‌شوند.
- **auth دقیقاً طبق بند ۴ همین فایل:** کوکی `access_token` (همان که REST
  استفاده می‌کند) مسیر اصلی است؛ تیکت یک‌بارمصرف
  (`POST /auth/ws-ticket`، TTL ۶۰ ثانیه در Redis، از فاز ۲) مسیر
  جایگزین است — با `GETDEL` اتمیک Redis مصرف می‌شود (نه GET+DEL جدا، که
  race را باز می‌گذاشت). اتصالی که هیچ‌کدام را نداشته باشد بلافاصله
  `disconnect` می‌شود؛ هیچ حالت «متصل ولی ناشناس» وجود ندارد.
- **`sendMessage()` payload broadcast شده عمداً فیلد `isMine` ندارد** —
  برخلاف پاسخ REST (که برای فرستنده همیشه `isMine:true` است)، این
  رویداد به همه‌ی اعضای room از جمله خودِ فرستنده می‌رسد؛ هر کلاینت باید
  خودش `senderId` را با شناسه‌ی کاربر خودش مقایسه کند.
- **بدون `EventEmitter2` یا event bus جدید.** ارتباط سرویس→گیت‌وی یک
  فراخوانی مستقیم متد است (`this.gateway?.broadcastMessage(...)`) —
  این کدبیس هیچ وابستگی event-bus از قبل ندارد و فقط یک نقطه‌ی فراخوانی
  دارد؛ اضافه‌کردن یک وابستگی جدید فقط برای همین یک مورد توجیه نداشت.
  پارامتر گیت‌وی در constructor سرویس **اختیاری** است (نه `@Inject`
  اجباری) تا تست‌های موجود (`new ConversationsService()` بدون آرگومان)
  بدون تغییر کار کنند؛ در مسیر واقعی (DI نستجی)، چون `ConversationsGateway`
  provider همان ماژول است، همیشه واقعی resolve می‌شود.
- **`app.useWebSocketAdapter(new IoAdapter(app))` صریح در `main.ts`
  اضافه شد** — به‌جای تکیه بر رفتار پیش‌فرض احتمالی نستجی، تا Socket.IO
  قطعاً روی همان HTTP server واقعی REST API متصل شود (بدون پورت جدا).

**تست:** ۸ تست جدید در `conversations.gateway.spec.ts` — بر خلاف بقیه‌ی
تست‌های این پروژه که سرویس را مستقیم صدا می‌زنند، این فایل یک اپ نستجی
واقعی را با `app.listen(0)` بالا می‌آورد (دقیقاً مثل
`users.body-validation.e2e.spec.ts`) و هم HTTP واقعی (`supertest`) هم
WebSocket واقعی (`socket.io-client`) را با هم ترکیب می‌کند: اتصال
بدون کوکی/تیکت قطع می‌شود؛ اتصال با کوکی معتبر باقی می‌ماند؛ مشارکت‌کننده‌ی
واقعی می‌تواند وارد room شود، غیرمشارکت‌کننده نمی‌تواند؛ ارسال واقعی از
طریق `POST /conversations/messages` به یک socket عضوشده می‌رسد، به
socket عضونشده نمی‌رسد؛ auth با تیکت کار می‌کند و تیکت واقعاً یک‌بارمصرف
است (تلاش دوم قطع می‌شود)؛ و یک تست مستقیم Redis ثابت می‌کند تیکت با
GETDEL واقعاً حذف شده، نه صرفاً منقضی.

**نکته‌ی روش‌شناسی کشف‌شده حین نوشتن این تست‌ها (نه یک باگ در کد خودِ
گیت‌وی):** اجرای منفرد این فایل تست با `npx jest <file>` (بدون بقیه‌ی
suite) پروسه را بعد از پاس‌شدن همه‌ی تست‌ها معلق نگه می‌داشت. بررسی نشان
داد این یک مشکل **از پیش موجود** در کل این کدبیس است، نه چیزی که این
PR ایجاد کرده باشد — همان رفتار روی `users.body-validation.e2e.spec.ts`
(فایلی که ماه‌ها پیش merge و در CI سبز شده) هم با `npx jest <file>`
منفرد بازتولید شد. علت: Jest وقتی یک فایل را با `--runInBand`-مانند
(یا تک‌فایلی) اجرا می‌کند، خودِ پروسه‌ی اصلی باید event loop خالی شود تا
خارج شود؛ در اجرای کامل suite (`pnpm test` واقعی، همان چیزی که CI اجرا
می‌کند)، Jest از worker process pool استفاده می‌کند که بعد از اتمام
تست‌های هر فایل، worker را مستقل از handleهای باز می‌بندد — همین باعث
می‌شود این مشکل هرگز در اجرای واقعی suite دیده نشود. **اثبات مستقیم:**
`pnpm test` کامل (دقیقاً دستور واقعی package.json) با همین فایل کنارِ
۴۴ فایل دیگر، ۳۲۹/۳۲۹ تست را در ۱۴ ثانیه پاس کرد و با کد خروجی ۰ دقیقاً
برگشت — بدون هیچ آویزان‌ماندنی. با این حال، برای سلامت toolها (نه برای
رفع خودِ رفتار Jest)، `afterAll` این فایل صریحاً `gateway.server.close()`
و `prisma.$disconnect()` را قبل از `app.close()` فراخوانی می‌کند —
نظافت درست، ولی رفع علت اصلی نیست (که خودِ معماری worker-pool جست است،
نه چیزی در کد این پروژه).

**اثبات زنده (خارج از Jest، سرور dev واقعی، Postgres/Redis/HTTP/WebSocket
واقعی، بدون mock به‌جز `SMS_PROVIDER=mock`):** با یک اسکریپت Node مستقل
(نه Playwright — برای این لایه یک کلاینت خام socket.io-client کافی و
دقیق‌تر بود) با سه کاربر واقعی (OTP واقعی): A درخواست ساخت و منتشر کرد،
B پیشنهاد داد، A انتخاب کرد → گفتگوی واقعی. سپس: اتصال A با کوکی واقعی
موفق شد؛ A وارد room شد (`{ok:true}`)؛ B با یک `POST /conversations/
messages` واقعی پیام فرستاد؛ A همان لحظه رویداد `message:new` را روی
socket دریافت کرد (بدنه‌ی پیام دقیقاً مطابق آنچه در Postgres نوشته شد)؛
کاربر سوم C (نه seeker نه provider) تلاش برای join کرد و `{ok:false}`
گرفت؛ یک تیکت واقعی از `POST /auth/ws-ticket` گرفته شد و برای اتصال
بدون‌کوکی استفاده و موفق شد؛ تلاش دوم با همان تیکت قطع شد
(`disconnected:true`) — اثبات زنده‌ی GETDEL یک‌بارمصرف. **یک باگ در خودِ
اسکریپت QA (نه در کد محصول) حین این اجرا کشف و رفع شد:** بررسی اول رویداد
`connect` مشتری را در برابر `disconnect` مسابقه می‌داد و همیشه `connect`
برنده می‌شد چون آن رویداد در لایه‌ی transport زودتر از تصمیم async سمت
سرور (`await redis.getdel(...)`) fire می‌شود؛ رفع با انتظار مشخص فقط
برای رویداد `disconnect` (نه یک مسابقه)، که رفتار واقعی صحیح
(«قطع می‌شود») را نشان داد — همان چیزی که تست Jest از ابتدا درست
سنجیده بود. تمام داده‌ی تستی (۶ کاربر، ۲ درخواست، ۲ پیشنهاد، ۲ گفتگو، از
دو اجرای اسکریپت) پاک شد؛ شمارش پایه‌ی seed بدون تغییر ماند: ۸ کاربر، ۱۵
درخواست، ۱۲ دسته، ۱۲ مهارت، ۲۰ پیشنهاد، ۲ گفتگو.

`pnpm lint`/`typecheck`/`test` کامل مونوریپو سبز؛ `apps/api` به‌تنهایی
۳۲۹ تست (۳۲۱ قبلی + ۸ گیت‌وی)، exit code صفر، بدون آویزان‌ماندن.

**تصحیح بعدی (بازبینی PR ۴ پایین):** جمله‌ی «فاز ۸ اکنون کاملاً تکمیل
است» که اینجا نوشته شده بود زودهنگام بود — این PR فقط گیت‌وی سمت سرور را
ساخت؛ `apps/web`ی `MessageThread` تا PR ۴ هیچ‌گاه واقعاً به یک socket
وصل نمی‌شد (بدون `socket.io-client` در `apps/web/package.json`، بدون
هیچ `io(...)` در کد). یعنی «تحویل بی‌درنگ» فقط در بک‌اند وجود داشت، نه
در تجربه‌ی واقعی کاربر.

### PR ۴ — اتصال UI به Socket.IO (تحویل واقعاً بی‌درنگ در مرورگر، تکمیل‌شده)

**چیستی این شکاف:** PR ۳ گیت‌وی را کامل و تست کرد، ولی هیچ‌کدام از دو
صفحه‌ی `apps/web` (فهرست/thread) هرگز از آن استفاده نکردند — `MessageThread`
فقط با REST بارگذاری می‌شد و برای دیدن پیام تازه‌ی طرف مقابل نیاز به رفرش
دستی صفحه داشت (دقیقاً همان محدودیت مستندشده در PR ۲ بالا، که با اشتباه
در جمع‌بندی PR ۳ به‌عنوان «حل‌شده» علامت خورد).

**تغییر:** `message-thread.tsx` یک `useEffect` جدید گرفت که با
`socket.io-client` (`io(BASE_URL, {withCredentials:true})`، دقیقاً همان
کوکی `access_token` که REST استفاده می‌کند) به گیت‌وی وصل می‌شود، بعد از
`connect` رویداد `conversation:join` را می‌فرستد، و روی `message:new`
پیام تازه را (اگر از قبل در state نبود) با `isMine` محاسبه‌شده محلی
(`payload.senderId === userId`) اضافه می‌کند. گفتگوهای `archived` این
effect را کلاً رد می‌کنند (چون `sendMessage()` آنجا رد می‌شود، چیزی هم
نمی‌رسد). `BASE_URL` از `api-client.ts` اکسپورت شد تا هم REST هم socket
از یک منبع بخوانند.

**باگ واقعی کشف‌شده با QA زنده (نه با typecheck/lint/build که هر سه از
قبل سبز بودند):** یک اسکریپت Playwright یک‌بارمصرف (دو `BrowserContext`
مستقل، جریان کامل OTP واقعی → ساخت/انتشار درخواست → پیشنهاد → انتخاب →
گفتگو → ارسال پیام واقعی از UI) روی سرور dev واقعی اجرا شد. در اولین
اجرای موفق، کنسول مرورگر فرستنده (نه گیرنده) هشدار واقعی React نشان داد:
«Encountered two children with the same key» — یعنی همان پیامی که
فرستاده بود، دوبار در state ظاهر می‌شد. علت ریشه‌ای (نه یک artifact
تستی): در `conversations.service.ts`، `sendMessage()` قبل از
`return`‌کردن پاسخ REST، `this.gateway?.broadcastMessage(...)` را صدا
می‌زند — روی یک اتصال loopback با تأخیر نزدیک صفر، این broadcast اغلب
زودتر از پاسخ HTTP خودِ همان درخواست به مرورگر فرستنده می‌رسد. نتیجه:
`handleIncoming` (شنونده‌ی socket) پیام را اول اضافه می‌کند؛ سپس
`handleSend` با پاسخ REST بدون هیچ چک تکراری همان پیام را دوباره
`push` می‌کرد. این یک ریسک واقعی production است (نه صرفاً یک حالت
dev/loopback)، چون هیچ تضمینی نیست که ترتیب واقعی HTTP در برابر
WebSocket چه باشد. رفع: `handleSend` هم اکنون همان گارد
`prev.some((m) => m.id === message.id)` را قبل از افزودن اجرا می‌کند —
متقارن با گارد موجود در `handleIncoming`، یعنی صرف‌نظر از ترتیب ورود دو
مسیر، پیام دقیقاً یک‌بار در state می‌نشیند.

**اثبات زنده (تکرار همان اسکریپت بعد از رفع، Postgres/Redis واقعی، دو
کاربر تازه با OTP واقعی):** B پیامی از UI فرستاد؛ A بدون رفرش صفحه (فقط
از طریق رویداد `message:new`) آن را دید؛ A پاسخ داد؛ B بدون رفرش پاسخ
را دید — هر دو جهت بدون هیچ هشدار کنسول. اسکرین‌شات نهایی هر دو طرف
گرفته شد (حباب فرستنده در انتهای منطقی/چپ بصری RTL طبق تصمیم PR ۲، حباب
طرف مقابل در ابتدای منطقی/راست بصری). **نکته‌ی جانبی از همین بررسی،
بدون ربط به این باگ:** یک بار جداگانه، بعد از چند اجرای پیاپی همین
اسکریپت روی سرور dev طولانی‌مدت (بالا از ساعت ۱۶:۰۰ همان روز)، صفحه‌ی
